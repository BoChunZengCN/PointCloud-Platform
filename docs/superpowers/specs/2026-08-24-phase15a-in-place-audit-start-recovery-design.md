# Phase 15A 审计启动原位恢复设计

**日期：** 2026-08-24

**状态：** 已确认并实现
**范围：** 仅处理审计操作初始化与幂等竞争恢复

## 1. 问题

当前审计启动流程会先创建操作状态投影，再发布幂等索引。如果索引发布竞争失败，或者在 `operation.started` 事件持久化前中断，现有实现会尝试删除或隔离尚未启动的操作目录。

跨平台路径清理逐步引入了以下风险：

- Windows 传统路径长度扩张；
- POSIX `rename` 覆盖语义；
- 符号链接和重解析点穿透；
- 路径检查与执行之间的身份竞态；
- 不安全的递归清理；
- 隔离目录容量和协调锁问题。

业务请求路径不需要删除或移动候选操作才能保证正确性。更安全的原则是：操作 ID 一旦分配，就成为不可变审计证据，不再自动回收或复用。

## 2. 目标

1. 从审计启动流程中移除自动重命名、隔离、递归删除和空目录删除。
2. 将每个成功写出的操作投影保留在其规范路径。
3. 在现有单操作内核锁下，将“已有投影但无事件”的状态收敛为：
   - 自身幂等发布成功时写入 `operation.started`；
   - 发布失败或其他操作获胜时写入 `operation.start_failed`。
4. 支持同一操作和请求在首个生命周期事件写入前发生进程中断后继续恢复。
5. 保持现有幂等获胜者重放和冲突语义不变。
6. 不在同步业务请求路径中增加新的固定锁文件、目录搬运或维护任务。

## 3. 非目标

- 初始化失败后回收操作 ID。
- 自动删除旧版本产生的历史隔离目录。
- 重新设计幂等索引格式或全部审计锁机制。
- 防御与服务进程使用相同操作系统身份、并能在系统调用期间主动替换任意项目文件的攻击者。

旧隔离目录作为历史诊断证据保持不动。后续可以提供显式管理员维护命令，在离线检查后清理；本次修改不再创建新的隔离目录。

## 4. 威胁与可靠性边界

本设计防护：

- 不可信 API 和 CLI 输入；
- 格式错误或内容不一致的投影、索引和事件；
- 投影、索引和首事件写入之间的进程中断；
- 使用现有内核锁的协作型并发进程；
- 已存在的生命周期冲突和幂等竞争。

项目存储根目录由服务所有者管理。能够以服务相同系统身份主动修改任意文件的攻击者不属于本阶段边界，因为该身份本身已经能够替换锁文件、源代码或审计账本。系统对已检测到的符号链接、重解析点、结构、指纹和生命周期异常仍然执行失败关闭。

## 5. 选定架构

### 5.1 不可变候选操作

创建操作目录即永久分配该操作 ID。业务请求流程不再重命名、递归删除或复用此目录。

现有 `operation.json` 继续作为初始化信封。恢复前必须精确核对执行者、角色、身份来源、请求 ID、操作类型、幂等键哈希、请求指纹、初始化所有者令牌和时间字段。

### 5.2 锁内初始化收敛

`start_operation` 在写入或恢复初始投影前，先获取现有单操作初始化锁。

在锁内执行：

1. 操作目录为新建时，写入初始投影。
2. 目录已包含相同且有效的运行中投影，并且没有生命周期事件时，恢复初始化。
3. 信封不同、数据损坏或生命周期证据与请求不一致时，不修改数据并失败关闭。
4. 幂等索引指向当前操作且指纹匹配时，只写入一次 `operation.started` 首事件。
5. 同一幂等键由其他操作获胜时，为当前失败候选写入一次 `operation.start_failed` 首事件，稳定错误码为 `idempotency_race_lost`，随后重放或拒绝获胜操作。
6. 幂等索引在可见前发布失败时，写入错误码为 `audit_persistence_error` 的 `operation.start_failed`，然后返回持久化错误。
7. 无法确认发布可见性时，保留运行中候选并返回 `audit_persistence_error`；重试时以实际可见索引为依据收敛，不猜测发布结果。

现有哈希链规则已经允许 `operation.start_failed` 作为终止型首事件，因此不新增生命周期事件类别。

### 5.3 中断恢复

只有冻结信封全部匹配时，同一请求才允许恢复规范的“运行中、无事件”投影。恢复不得依赖经过时间。

| 中断后的持久状态 | 重试行为 |
| --- | --- |
| 目录存在但投影不存在 | 在初始化锁内重新创建完全一致的投影 |
| 投影匹配、索引不存在 | 重试原子不覆盖的索引发布 |
| 投影匹配、自身索引可见 | 只补写一次 `operation.started` |
| 投影匹配、其他获胜者可见 | 只写一次 `operation.start_failed`，随后重放获胜者 |
| `operation.start_failed` 已持久化 | 对该操作 ID 重放稳定终止错误 |
| 任意不匹配或证据损坏 | 使用稳定完整性或持久化错误失败关闭 |

### 5.4 并发

- 单操作锁负责串行化初始化和生命周期收敛。
- 现有原子不覆盖幂等发布负责在不同操作 ID 之间选择唯一获胜者。
- 每个失败候选独立终止，不再需要全局隔离锁。
- 初始化仍存活时返回稳定的 `operation_busy`；后续重试执行同一套确定性恢复。

## 6. 被否决的方案

### 6.1 跨平台安全隔离目录

该方案需要平台专用的不覆盖重命名、路径身份回滚、安全递归删除、容量上限和新的可信协调锁。此前实现表明，每增加一个保护层就会产生新的检查—执行边界。候选操作可以安全留在规范路径，因此没有必要承担这部分复杂度。

### 6.2 先发布幂等索引，再创建操作

该方案可以避免生成失败候选目录，但进程中断可能留下指向不存在操作的索引。正确恢复要求在新索引格式中保存完整初始化信封并迁移既有索引，属于后续整体重构，不属于 Phase 15A 稳定性修复。

## 7. 错误与审计语义

- `operation_busy`：仍有初始化进程持有单操作锁。
- `operation_exists`：操作 ID 已绑定到其他不可变信封或终止操作。
- `idempotency_conflict`：幂等键已绑定到不同请求指纹。
- `idempotency_race_lost`：仅记录在竞争失败的候选操作上；调用方仍取得获胜者的正常重放或冲突结果。
- `audit_persistence_error`：无法确认发布或状态收敛。
- `audit_integrity_error`：持久化证据格式错误或互相矛盾。

事件明细不得写入原始请求值、路径、令牌或可能包含敏感信息的异常文本。审计身份继续使用规范请求指纹和可信主体字段。

## 9. 验收测试

1. 幂等竞争失败的候选保留在规范路径，并且只有一个有效的 `operation.start_failed` 首事件。
2. 获胜操作重放成功，且不产生重复生命周期事件。
3. 投影写入后、索引发布前中断时，相同信封能够恢复并只完成一次。
4. 自身索引发布后、`operation.started` 写入前中断时，只补写一次缺失事件。
5. 不同信封复用同一操作 ID 时，不修改已保留操作并稳定失败。
6. 多个不同操作 ID 并发使用同一幂等键时，只产生一个启动成功的获胜者和已终止的失败候选，不出现全局锁错误。
7. 索引发布失败但审计存储仍可写时，记录稳定的启动失败。
8. 审计启动路径不调用目录重命名、递归删除、隔离或空目录删除。
9. 既有审计、模型库、模型导入、API 和 CLI 聚焦测试保持通过。
10. 完成就绪门禁时运行一次全量测试；只有明确要求推送时才在推送前再运行一次。

## 10. 交付边界

- 一个架构实现提交。
- 最多一个复审修正提交。
- 聚焦验证后只进行一次独立最终复审。
- 如果再次出现同类清理或 TOCTOU 问题，立即停止，不在本阶段重新引入隔离补丁。
